# Bad Case 分析与修复记录

| 场景 | 发现 | 修复与回归保障 |
| --- | --- | --- |
| 订单状态被识别为物流 | 模型可能把“发货了吗”判为物流查询 | 对明确“发货状态”与“到哪/派送”词组进行受限纠偏；工具测试覆盖。 |
| 缺少订单号 | 模型可能臆造 `12345` 并触发查询 | 只接受当前用户问题中显式出现的订单号；缺失时追问且不创建工具记录。 |
| 转人工审计 | UUID 写入 JSONB 曾触发 500 | 工具输入经 JSON 兼容序列化；真实接口验收确认工单与审计成功。 |
| 审计密钥泄露 | `Authorization: Bearer <token>` 的脱敏顺序可残留 token | Bearer 值优先脱敏，写入与读取 JSON 均按敏感字段名递归脱敏；回归测试覆盖。 |
| 非聊天请求不可追溯 | 早期只记录了聊天请求 | 全局审计中间件记录每个路由的请求 ID、身份、路径、方法、状态与耗时；聊天保留更完整的改写、意图、检索、工具与 LLM 用量。 |

## 后续观察

`evals/cases.json` 是版本化验收场景的来源。针对稳定业务语料，应定期执行其中的 RAG 与工具案例，统计回答正确性、来源正确性、幻觉率、完整性与工具参数正确性，并据此调整检索阈值和 Prompt。
